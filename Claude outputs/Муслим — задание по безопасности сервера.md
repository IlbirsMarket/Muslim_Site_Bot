# Кафе «Муслим» — защита сервера: пошаговое задание

> **Как пользоваться.** Вставьте этот файл целиком в начало чата с Claude. Claude ведёт человека по шагам, а команды на сервере человек вводит сам. Всё ниже верно на 30.10.2026.
> Сервер принадлежит Мухаммадамину. Работать **вместе с ним** или с его разрешения.

---

## 0. Правила (обязательно)

1. **Русский язык, простыми словами.** Один шаг — одна-три команды. После каждого шага человек присылает вывод, Claude проверяет его и только потом даёт следующий шаг.
2. **Пароли, ключи и токены никогда не пишутся в чат.**
   - Секретный (приватный) SSH-ключ никуда не копировать.
   - Содержимое `.env` не показывать: только проверки вида «есть ли строка», «какой длины».
   - Вставлять в чат можно только **публичный** ключ (`.pub`).
3. **Claude сам не входит на сервер и не вводит пароли.** Все команды выполняет человек.
4. **Не запереть себя снаружи:**
   - старое окно SSH держать открытым до конца шага;
   - вход по паролю отключать **последним**, когда вход по ключу уже проверен **в новом окне**;
   - запасной вход — консоль DigitalOcean в браузере: Droplet → Access → **Droplet Console** / **Recovery Console**.
5. Перед изменением настроек — резервная копия файла: `cp файл файл.bak-ДАТА`.
6. После изменения настроек nginx или SSH — сначала проверка (`nginx -t`, `sshd -t`), и только если она прошла, перезапуск.
7. Сайт — рабочий: проверять, что сайт и бот работают **после каждого** шага.

## 3. Шаги подробно

### Шаг 1. Обновить систему (под root, пока как сейчас)

```bash
apt update && apt -y upgrade
```

Если попросит перезагрузку (`/var/run/reboot-required` существует):

```bash
reboot
```

Через минуту снова зайти и проверить:

```bash
systemctl is-active nginx muslim muslim-bot
```

Должно быть три раза `active`.

### Шаг 2. Администратор с sudo

Имя придумайте сами, например `admin1`. **Не** `admin` и не `muslim`.

```bash
adduser admin1
usermod -aG sudo admin1
```

Пароль для `admin1` придумывает человек: длинный, нигде не используемый. В чат его не писать. Он нужен для `sudo`, но не для входа по SSH.

### Шаг 3. SSH-ключ

**На своём компьютере** (Windows: PowerShell; macOS/Linux: терминал):

```powershell
ssh-keygen -t ed25519 -C "muslim-server"
```

- Где сохранить — Enter (по умолчанию `C:\Users\<имя>\.ssh\id_ed25519`).
- Пароль к ключу (passphrase) — **поставить**. Без него украденный файл ключа сразу открывает сервер.

Показать **публичный** ключ (его можно вставить в чат для проверки формата):

```powershell
type $env:USERPROFILE\.ssh\id_ed25519.pub
```

Строка начинается с `ssh-ed25519 AAAA…` и заканчивается `muslim-server`.

**На сервере** (под root), положить ключ администратору:

```bash
mkdir -p /home/admin1/.ssh
nano /home/admin1/.ssh/authorized_keys      # вставить ОДНУ строку ssh-ed25519 … и сохранить
chown -R admin1:admin1 /home/admin1/.ssh
chmod 700 /home/admin1/.ssh
chmod 600 /home/admin1/.ssh/authorized_keys
```

**Проверка — в НОВОМ окне PowerShell** (старое не закрывать!):

```powershell
ssh admin1@207.154.243.128
```

Должно спросить **passphrase ключа**, а не пароль пользователя. Затем:

```bash
sudo whoami
```

Должно ответить `root`. Если не получилось — разобраться, **не переходя к шагу 4**.

> Каждому, кто будет заходить на сервер, — свой ключ и, лучше, свой пользователь. Общих ключей не делать.

### Шаг 4. Закрыть вход root и вход по паролю

**Только после того, как шаг 3 работает в новом окне.**

```bash
sudo cp /etc/ssh/sshd_config /etc/ssh/sshd_config.bak-$(date +%F)
sudo nano /etc/ssh/sshd_config.d/00-muslim.conf
```

Содержимое файла:

```
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
PubkeyAuthentication yes
MaxAuthTries 3
LoginGraceTime 30
X11Forwarding no
AllowUsers admin1
```

Проверить и применить:

```bash
sudo sshd -t && sudo systemctl reload ssh
```

`sshd -t` ничего не пишет — значит, ошибок нет.

**Проверка в НОВОМ окне:**
- `ssh admin1@207.154.243.128` — входит по ключу;
- `ssh root@207.154.243.128` — должен быть **отказ**.

Если что-то сломалось, войти через консоль DigitalOcean, удалить `/etc/ssh/sshd_config.d/00-muslim.conf` и выполнить `systemctl reload ssh`.

> Важно: в Ubuntu 24.04 в папке `/etc/ssh/sshd_config.d/` уже может лежать файл (например, `50-cloud-init.conf`) с `PasswordAuthentication yes`. SSH берёт **первое** найденное значение, а файлы читает по алфавиту, поэтому наш назван `00-…`: он читается раньше. Строку `PasswordAuthentication yes` в чужом файле всё равно лучше закомментировать (`#`). Проверить:
> ```bash
> sudo grep -ri "passwordauthentication" /etc/ssh/sshd_config /etc/ssh/sshd_config.d/
> sudo sshd -T | grep -E "permitrootlogin|passwordauthentication"
> ```
> Итог должен быть: `permitrootlogin no`, `passwordauthentication no`.

### Шаг 5. Файрвол UFW

```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow OpenSSH          # 22
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp          # пригодится для HTTPS
sudo ufw limit OpenSSH          # не больше 6 попыток подключения за 30 с с одного IP
sudo ufw enable
sudo ufw status verbose
```

Порт 8000 (gunicorn) **не** открывать: он слушает только `127.0.0.1`. Проверить:

```bash
sudo ss -tlnp | grep -E ":8000|:80 |:22 "
```

`8000` должен быть только на `127.0.0.1`.

**Дополнительно (рекомендуется):** Cloud Firewall в панели DigitalOcean (Networking → Firewalls) с теми же правилами 22/80/443. Это защита «снаружи» сервера.

### Шаг 6. fail2ban

```bash
sudo apt -y install fail2ban
sudo nano /etc/fail2ban/jail.local
```

Содержимое:

```ini
[DEFAULT]
bantime = 1h
findtime = 10m
maxretry = 5

[sshd]
enabled = true
backend = systemd

[nginx-limit-req]
enabled = true
backend = auto
logpath = /var/log/nginx/error.log

[nginx-botsearch]
enabled = true
backend = auto
logpath = /var/log/nginx/access.log
```

```bash
sudo systemctl enable --now fail2ban
sudo fail2ban-client status
sudo fail2ban-client status sshd
```

> Если окажется, что заблокировали себя: войти через консоль DigitalOcean и выполнить `sudo fail2ban-client set sshd unbanip <ваш IP>`.

### Шаг 7. Автообновления безопасности

```bash
sudo apt -y install unattended-upgrades
sudo dpkg-reconfigure -plow unattended-upgrades     # ответить «Yes»
cat /etc/apt/apt.conf.d/20auto-upgrades
```

Должно быть `Update-Package-Lists "1"` и `Unattended-Upgrade "1"`. Автоматическую перезагрузку **не включать**: перезагрузку делать вручную, в тихое время.

### Шаг 8. Права на файлы и секреты

```bash
sudo chown muslim:muslim /home/muslim/app/.env /home/muslim/app/db.sqlite3
sudo chmod 600 /home/muslim/app/.env
sudo chmod 640 /home/muslim/app/db.sqlite3
ls -la /home/muslim/app/.env /home/muslim/app/db.sqlite3
```

Права на саму папку `/home/muslim` **не менять**: через неё nginx читает сайт (`frontend/dist`) и фото (`media`). После шага открыть сайт и убедиться, что меню и фото на месте.

Проверить `.env` **без вывода секретов** (под `muslim`):

```bash
sudo -u muslim bash -c 'cd ~/app && grep -c "^DJANGO_ADMIN_URL=manage-" .env && venv/bin/python -c "from dotenv import dotenv_values as d; print(len(d(\".env\").get(\"SECRET_KEY\") or \"\"))"'
```

Ожидается `1` и число **≥ 50**.

Убедиться, что `.env` и база не попали в git:

```bash
sudo -u muslim git -C /home/muslim/app ls-files | grep -E "^\.env$|db\.sqlite3" || echo "OK — в git их нет"
```

### Шаг 9. Резервные копии вне сервера

Сейчас копия базы лежит на том же сервере: если сломается диск или сервер взломают, пропадёт и она.

1. **DigitalOcean Backups** (панель → Droplet → Backups → Enable): +20% к цене сервера, еженедельная копия всего сервера. Самое простое.
2. Дополнительно — копия базы раз в сутки **за пределы сервера**: DigitalOcean Spaces или другое хранилище по выбору владельца. Доступ к хранилищу — только на запись, ключи хранятся в `.env` или в отдельном файле с правами 600.
3. Раз в месяц **пробовать восстановление** на тестовой машине. Копия, которую ни разу не восстанавливали, может не сработать, когда понадобится.

### Шаг 10. Итоговая проверка и отчёт

```bash
sudo sshd -T | grep -E "permitrootlogin|passwordauthentication"
sudo ufw status
sudo fail2ban-client status
systemctl is-active nginx muslim muslim-bot fail2ban unattended-upgrades
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1/
```

Ожидается:
- `no` / `no`;
- `Status: active` (22, 80, 443);
- jails `sshd`, `nginx-…`;
- все службы `active`;
- сайт отвечает `200`.

Открыть в браузере `http://207.154.243.128/` и `/admin`: меню и вход работают.

**Отчёт владельцу** (без секретов):
- что сделано;
- имя пользователя-администратора;
- у кого есть ключи;
- где копии;
- что осталось (HTTPS).

### Шаг 11. Позже: домен и HTTPS (последний этап)

Делается, когда шеф купит домен `.com`; рекомендуемый регистратор — Cloudflare Registrar.

- DNS: запись `A` `@` и `www` → `207.154.243.128`.
- Сертификат: `sudo apt -y install certbot python3-certbot-nginx`, затем `sudo certbot --nginx -d домен -d www.домен`. Продление автоматическое; проверка — `sudo certbot renew --dry-run`.
- В `/home/muslim/app/.env`:
  - `USE_HTTPS=1`;
  - `ALLOWED_HOSTS` — домен;
  - `CSRF_TRUSTED_ORIGINS=https://домен`;
  - `SITE_URL=https://домен`.
- В nginx `server_name домен www.домен;`. Порт 80 перенаправляет на 443 (certbot делает это сам).
- После этого заново скачать **все QR** (столы и доставка обоих филиалов): адрес в них станет `https://домен/t/…`.
- Это делается вместе с Мухаммадамином: затрагиваются настройки сайта.

## 4. Чего не делать

- Не отключать вход по паролю, пока вход по ключу не проверен в новом окне.
- Не открывать порт 8000 и не менять `bind` у gunicorn.
- Не копировать приватные ключи между людьми и не присылать их в чат.
- Не запускать на сервере `python manage.py seed_demo`: он и так откажется работать.
- Не трогать код сайта и `deploy/nginx-muslim.conf` без согласования с Мухаммадамином.
- Не перезагружать сервер в часы работы кафе без предупреждения.
